Core LLM concepts (glossary)

Token
The unit an LLM reads and writes: a word piece, whole short word, or punctuation. Roughly 1 token ≈ ¾ of an English word. Cost, speed and limits are all counted in tokens.
Context / Context window
Context is everything the model sees for one call: system prompt, conversation history, retrieved documents, your question. The context window is the maximum tokens (input + output) it can handle at once. Anything outside it does not exist for the model.
Vector
A list of numbers, e.g. [0.12, -0.8, 0.33, …].
Vector embedding
A vector produced by an embedding model that captures the meaning of a text (or image). Similar meanings → vectors that sit close together. This is what makes semantic search possible.
Transformer
The neural network architecture behind modern LLMs. Its key idea is attention: while processing each token, the model weighs how relevant every other token is, so it can use context (e.g. what "it" refers to).
Pre-training
The expensive first stage: training on huge amounts of text to predict the next token. Produces a base model with broad language and world knowledge, frozen at a knowledge cutoff.
Fine-tuning
Further training of a pre-trained model on a smaller, specific dataset to change its style, format or skill (e.g. instruction-following, domain tone). Changes the model's weights. Good for behaviour, poor for injecting fresh facts. (LoRA/QLoRA = cheap variants that train small adapter weights.)
Inference
Using a trained model to generate output (what happens on every API call). No learning occurs; weights are unchanged.
Temperature
Controls randomness when picking the next token. 0 ≈ deterministic and focused (extraction, code); higher (0.7–1.0) = more varied and creative.
Top-p (nucleus sampling)
Sample only from the smallest set of tokens whose probabilities add up to p (e.g. 0.9). Cuts off unlikely tokens.
Top-k
Sample only from the k most likely tokens (e.g. 40). Usually tune temperature or top-p, not both.
Max tokens
Cap on output length. Too low → answer is cut off.
AI agent
An LLM running in a loop with tools (search, code, APIs, DB queries): it decides what to do, calls a tool, observes the result, and repeats until the goal is met. Chatbot answers; agent acts.
Harness
The code around the model that makes it useful as an agent: the loop, tool definitions and execution, prompt assembly, memory/context management, permissions, retries and guardrails. Claude Code is a harness around Claude. Same model + different harness = very different results.
Hallucination
Fluent but false or invented output. Happens because the model predicts plausible text, not verified truth.
RAG (Retrieval-Augmented Generation)
Fetch relevant chunks from your own documents at question time and put them in the prompt, so the answer is grounded and citable. See the RAG section below.
Prompt injection
Malicious text (in a user message or a retrieved document) that tries to override the model's instructions.

GenAI & LLM fundamentals + prompt engineering

Generative AI vs traditional ML

Traditional ML classifies or predicts from structured features (fraud yes/no, price forecast) and needs a model trained per task. Generative AI creates new content (text, code, images) and one general model handles many tasks via instructions.

How LLMs work

  • Trained on large text corpora to predict the next token; repeating this builds whole answers.
  • Transformer + attention lets each token look at all others to capture context.
  • Stages: pre-training → fine-tuning / instruction tuning → (RLHF-style alignment) → inference.

Model families

FamilyTypeNotes
OpenAI GPTClosed (API)Strong general models, wide ecosystem, Azure OpenAI for enterprise
Anthropic ClaudeClosed (API)Strong coding, long context, careful/safe behaviour
Google GeminiClosed (API)Multimodal, very long context, Google Cloud integration
Meta LlamaOpen weightsSelf-host, fine-tune, full data control
MistralOpen + closedEfficient models, good European/self-host option

Closed = best quality, easy, pay per token, data leaves your boundary. Open = control, privacy, fine-tuning, no per-token fee, but you run the infra.

Limitations

  • Hallucination — reduce with RAG grounding, "answer only from context / say I don't know", low temperature, citations, validation, human review.
  • Knowledge cutoff — doesn't know recent or private data → RAG or tools.
  • Cost per token and latency grow with prompt size and model size.
  • Data privacy — sending confidential data to a third-party API; use enterprise agreements, private deployments or open models.

Prompt engineering techniques

TechniqueIdea
System prompt / roleSets persona, rules, tone, output format ("You are a finance analyst…")
Zero-shotInstruction only, no examples
Few-shotInclude 2–5 input→output examples; improves format and consistency
Chain-of-thoughtAsk it to reason step by step before answering; helps multi-step problems
Structured outputAsk for JSON (or use schema/tool mode), then validate (e.g. Pydantic) and retry on failure
Prompt templatesFixed prompt with {variables} filled at runtime — reusable and testable

Prompt safety

  • Prompt injection: hostile instructions hidden in user input or retrieved docs ("ignore previous instructions…").
  • Jailbreaks: tricks to bypass the model's safety rules.
  • Guardrails: input/output filters, treat retrieved text as data not instructions, least-privilege tools, output validation, PII redaction, human approval for risky actions.

Prompting vs fine-tuning vs RAG

NeedUse
Clear task, format, tone; fast startPrompting (try first)
Answers from private / changing documents, citationsRAG
Consistent style/behaviour, specialised skill, smaller cheaper modelFine-tuning
Rule of thumb: RAG gives the model knowledge, fine-tuning shapes its behaviour. They combine well.

Context window and RAG

You can't paste all documents into the prompt: the window is limited, more tokens cost more and slow things down, and models lose focus in very long context. RAG therefore must select only the few most relevant chunks that fit.

RAG concepts & enterprise pipelines

Why: LLMs don't know your private data and can hallucinate. RAG retrieves relevant text from your documents and gives it to the LLM as context → grounded answers with sources. Cheaper and easier to update than fine-tuning.

Pipeline at a glance

Ingest → Chunk → Embed → Index (vector DB)          (offline)
Question → Rewrite → Retrieve → Rerank → Build context → Generate → Evaluate   (online)
StageWhat it doesIf done badly
1. IngestionLoad PDF/Word/HTML/Confluence/SharePoint; parse tables & images; clean text; keep metadata (source, date, department)Garbled text, lost tables, no way to filter or cite
2. ChunkingSplit into pieces: fixed-size, recursive, sentence, semantic. Tune size/overlap; keep headings with contentToo big: noisy, diluted match. Too small: loses context. No overlap: answers cut across boundaries
3. EmbeddingsChunks → vectors. Models: OpenAI, Cohere, BGE, E5; consider multilingualPoor model/language fit → wrong neighbours
4. IndexingStore vectors + metadata in a vector DBSlow queries, no filtering, stale data
5. RetrievalSimilarity search, top-k, metadata filters, hybrid (BM25 + vector), query rewriting, multi-queryMisses exact terms/IDs, wrong department's docs, relevant chunk never found
6. RerankingCross-encoder / rerank API (e.g. Cohere Rerank) re-scores top candidatesBest chunk buried at rank 8 and cut off
7. Context managementFit window, order, dedupe, compressOverflow, duplicates, "lost in the middle"
8. GenerationPrompt: answer only from context, cite sources, say "I don't know"Hallucination, no citations
9. EvaluationRetrieval: recall, precision. Answer: faithfulness, relevance (RAGAS, DeepEval)You can't tell if changes help

Key ideas

  • Chunk size: typical 300–1000 tokens with 10–20% overlap; test on your own questions.
  • Hybrid search: vector search finds meaning; BM25 keyword finds exact terms (codes, names). Combining beats either alone.
  • Reranking: retrieve broadly (e.g. top 30) cheaply, then a slower, more accurate model picks the best 3–5.
  • RAG vs fine-tuning: RAG for facts that change and need citations; fine-tuning for style/behaviour.

Advanced patterns (know the names)

  • Parent-document retrieval — search small chunks, return the larger parent for context.
  • GraphRAG — build a knowledge graph of entities/relations to answer multi-hop questions.
  • Agentic RAG — an agent decides when/what to retrieve, can re-query and use multiple sources.
  • Document updates & access permissions — re-index changed docs, delete old vectors, filter results by user permission via metadata.

Vector databases & embeddings

The one-line idea: a vector database stores embeddings (meaning as numbers) and quickly finds the ones closest to a query embedding. It is the "search engine" inside a RAG system, but it searches by meaning instead of exact words.

1. What an embedding is

An embedding model reads text and outputs a fixed-length list of numbers (a vector). Texts with similar meaning get vectors that are close together, even if they share no words.

embed("How do I reset my password?")   → [0.021, -0.113, 0.447, … 1536 numbers]
embed("I forgot my login credentials") → [0.019, -0.098, 0.452, … ]   ← very close
embed("Quarterly revenue grew 12%")     → [-0.310, 0.205, -0.071, … ] ← far away
  • Dimensions = length of the list (e.g. 384, 768, 1536, 3072). More dimensions can capture more nuance but cost more storage and search time.
  • Each dimension has no human-readable meaning on its own; only the distances between vectors matter.
  • Queries and documents must be embedded with the same model. Vectors from different models live in different "spaces" and can't be compared.
  • Changing the embedding model later means re-embedding everything.
  • Embeddings also exist for images and audio (multimodal), so a text query can find a picture. See how below.
Why this beats keyword search: searching "car insurance claim" finds a chunk titled "Filing a motor vehicle accident report" because the meanings are near. Keyword search would miss it. The reverse weakness: embeddings can blur exact things like product code XJ-4421, which is why hybrid search exists.

2. Similarity measures

Once text is a vector, "how related are these two texts?" becomes "how close are these two vectors?".

MeasureWhat it measuresRange / readingWhen
Cosine similarityAngle between vectors, ignoring length−1 to 1; closer to 1 = more similarDefault for text embeddings
Dot productAngle and lengthLarger = more similarSame ranking as cosine when vectors are normalised (length 1); fastest. Some models are trained for it
Euclidean (L2)Straight-line distance0 = identical; smaller = more similarWhen magnitude matters; common in image/other embeddings

Tiny example (2 dimensions): query Q=[1, 0], doc A [0.8, 0.6], doc B [0, 1].

  • cosine(Q, A) = 0.8 → fairly similar
  • cosine(Q, B) = 0 → unrelated (vectors at 90°)

Real vectors have hundreds or thousands of dimensions, but the logic is identical. Always use the metric the embedding model recommends, and set the same metric when you create the index.

3. Indexing & approximate nearest neighbour (ANN)

The problem: exact ("brute-force") search compares the query with every stored vector. For 10 million vectors × 1536 dimensions that is far too slow for an interactive app.

The fix: ANN indexes organise vectors so a search only checks a small, promising slice. You trade a little accuracy (maybe 95–99% recall of the true top results) for orders-of-magnitude speed.

AlgorithmHow it works (intuition)Pros / cons
HNSW (Hierarchical Navigable Small World)Builds a layered graph. Start at a sparse top layer, jump to the neighbour closest to the query, drop down a layer, repeat. Like navigating a country → city → street.Very fast and accurate; the most popular. Uses a lot of RAM and builds slowly
IVF (Inverted File)Pre-cluster vectors into e.g. 1,000 groups. At query time find the nearest few cluster centres and search only inside those.Lower memory, faster build. Accuracy depends on how many clusters you probe (nprobe)
PQ (Product Quantisation) (often combined with IVF)Compresses vectors into short codesBig memory saving, some accuracy loss

Memory example: 1M vectors × 1536 dims × 4 bytes (float32) ≈ 6 GB before index overhead. 100M vectors ≈ 600 GB, which is why compression, smaller dimensions or disk-based indexes matter at scale.

Tuning knobs you'll meet: HNSW M and efSearch (higher = better recall, slower); IVF nlist / nprobe. Always measure recall against a brute-force baseline on your own data.

4. Metadata filtering & hybrid search

Each vector is stored with metadata, e.g. {"source":"HR-policy.pdf","department":"HR","year":2025,"access":"all-staff"}.

query:  "What is the parental leave policy?"
filter: department = "HR" AND year >= 2024 AND access IN user.groups

Why it matters in enterprise:

  • Security – a junior employee must not get finance board papers back from a semantic search. Permission filters enforce this at retrieval time (before the LLM ever sees the text).
  • Relevance – restrict to the right product, region, language or latest version.
  • Multi-tenancy – each customer only searches their own data.
  • Efficiency – a filter shrinks the search space.

Pre-filter vs post-filter: pre-filtering restricts candidates first (correct but harder on ANN indexes); post-filtering searches top-k then drops non-matching results, which can leave you with zero results if the top-k all fail the filter. Check how your database handles this.

Hybrid search: run keyword search (BM25) and vector search, then merge scores (e.g. Reciprocal Rank Fusion). Example: the query "error E-4021 on invoice upload" – BM25 nails the exact code, vectors capture "invoice upload problem" phrasing; together they beat either alone.

5. Scaling concerns

ConcernWhat to think about
Number of vectorsThousands: anything works. Millions: pick a proper index (HNSW/IVF). Hundreds of millions: sharding, quantisation, disk-based indexes
LatencyTarget is usually tens of ms per query; embedding the query and reranking often cost more than the DB search itself
CostRAM is the main driver (self-hosted); managed services bill per storage + queries. Cut with lower dimensions or quantisation
Updates & deletesDocuments change. Store a document ID in metadata so you can delete and re-insert all chunks of an edited file. Some indexes handle deletes poorly and need periodic rebuild
Multi-tenancySeparate collections/namespaces per tenant (strong isolation) vs one collection with a tenant filter (simpler, cheaper)
Durability / backupRe-embedding is slow and costs money; keep source docs and back up the index

6. Choosing an embedding model

  • Quality: check the MTEB leaderboard, but look at the retrieval score and test on your documents and questions; a leaderboard leader is not guaranteed to win on your domain (legal, medical, code).
  • Dimensions: 384 (small, cheap, e.g. MiniLM) → 1024 (BGE-large) → 1536/3072 (OpenAI text-embedding-3). Some models support shortening vectors (Matryoshka) to save space.
  • Cost & hosting: API models (OpenAI, Cohere) are easy and pay per token; open-source (BGE, E5) run locally for privacy and no per-call fee but need compute.
  • Language: for non-English or mixed-language content use a multilingual model (e.g. multilingual-E5, BGE-M3, Cohere multilingual).
  • Max input length: must fit your chunk size (e.g. 512 vs 8192 tokens).

8. How to choose (examples)

  • "I'm learning / building a demo" → Chroma or FAISS.
  • "Our app already uses PostgreSQL, ~1–5M chunks" → pgvector. No new system to run.
  • "Small team, need production fast, no ops" → Pinecone or a managed Qdrant/Weaviate.
  • "Data must stay in our network, need hybrid search" → self-hosted Qdrant, Weaviate or Milvus.
  • "We're an Azure shop with strict compliance" → Azure AI Search.

Decision factors: data size, existing stack, hosting/privacy rules, need for hybrid search and filtering, team ops skills, budget.

Images & audio: embeddings and generation

The one-line idea: a neural network cannot read pixels or sound waves directly as "meaning". Every modality is first turned into numbers (a tensor), then an encoder compresses those numbers into a vector. Once it is a vector, all the vector DB ideas above (similarity, ANN, filtering) work exactly the same.

1. Images → vector embedding

image file → resize/normalise → pixel grid (e.g. 224×224×3 numbers)
           → split into patches (16×16 pixels each)
           → vision encoder (ViT: a transformer over patches, or a CNN)
           → pooled output → vector, e.g. [0.07, -0.31, 0.52, … 512 numbers]
  • Pixels: an image is just a grid of numbers (red, green, blue per pixel). Raw pixels are a poor "meaning" signal: the same cat shifted a few pixels is a very different grid.
  • Patches: a Vision Transformer cuts the image into small squares and treats each patch like a token. Attention then lets patches relate to each other (an ear belongs with a head).
  • Training signal: the encoder learns from labels, from reconstruction, or (most useful for search) from image + caption pairs.

2. CLIP: one space for text and images

CLIP-style models train two encoders at once, an image encoder and a text encoder, on hundreds of millions of image–caption pairs. Contrastive learning pulls a photo and its caption together in vector space and pushes mismatched pairs apart.

embed_image(photo_of_dog.jpg)  → [0.12, 0.44, -0.20, …]
embed_text("a dog on a beach") → [0.10, 0.47, -0.18, …]   ← close
embed_text("a tax invoice")    → [-0.52, 0.03, 0.61, …]   ← far
  • This is what makes text → image search, image → image search and zero-shot classification work: compare vectors, nothing else.
  • Same rules as text: use the same model for both sides, same metric (usually cosine), re-embed if you change model.
  • Examples: OpenAI CLIP, SigLIP, Cohere Embed (multimodal), Google multimodal embeddings, Jina CLIP.

3. Audio / voice → vector embedding

audio file (waveform: 16,000 samples per second)
   → resample to a fixed rate, mono
   → spectrogram (time × frequency picture; often mel-scale)
   → audio encoder (CNN or transformer, e.g. wav2vec2 / Whisper encoder)
   → vector (one per clip, or one per short time frame)

A spectrogram turns sound into an image-like grid, so audio models borrow a lot from vision models. What the vector captures depends on what the model was trained for:

GoalModel typeVector representsUse
What was saidSpeech recognition (Whisper, wav2vec2)Phonetic / linguistic content per frame, decoded to textTranscribe, then embed the text for RAG over calls and meetings
Who is speakingSpeaker embedding (x-vector, ECAPA-TDNN)Voice identity, independent of wordsSpeaker verification, diarisation ("who spoke when"), voice cloning input
What it sounds likeAudio-text contrastive (CLAP)General sound meaning, shared space with textSearch "dog barking" or "upbeat piano" across audio
Practical shortcut: for "search my meetings" you rarely embed the audio itself. Transcribe with Whisper, chunk the transcript, and use a normal text embedding model. Embed the audio directly only when the sound itself matters (speaker, music, sound effects).

4. How the multimodal pieces connect to an LLM

  • Separate encoders, shared space: CLIP / CLAP. Good for retrieval, no text generation.
  • Encoder → projector → LLM (vision-language models): the image encoder's patch vectors are mapped by a small projection layer into the LLM's token embedding space, so image patches act like extra "tokens" the LLM attends to. This is how GPT-4o-style, Gemini, Claude and LLaVA/Llama-vision models "see".
  • Audio in LLMs: either a speech-to-text step first, or an audio encoder whose output is projected into the LLM the same way.
image → vision encoder → patch vectors → projector → [img tok][img tok]…
                                                          + text tokens "What is in this photo?"
                                                          → LLM → text answer

5. Generation: how new images and audio are made

Generation is the reverse direction: start from a prompt (usually an embedding of the text) and produce pixels or a waveform.

ApproachIntuitionUsed for
DiffusionTraining: take a real image, add noise step by step until it is static, and teach the network to remove a little noise at each step. Generation: start from pure random noise and denoise it step by step, steered by the text embedding.Stable Diffusion, DALL·E 3, Midjourney, Imagen; also video (Sora-style) and audio (Stable Audio)
Latent diffusionDo the denoising in a small compressed "latent" space made by an autoencoder (VAE), not on full pixels. Decode to pixels only at the end. Much cheaper.Stable Diffusion family
Autoregressive tokensTurn the image or audio into discrete tokens with a codec/tokenizer, then predict the next token exactly like an LLM. Decode tokens back to pixels or sound.Parti, some GPT/Gemini image output, MusicGen, audio LMs
GAN (older)A generator and a discriminator compete; the generator improves by fooling it.Face synthesis, upscaling. Largely replaced by diffusion

6. Text prompt → image (step by step)

"a red bicycle at sunset"
 1. text encoder (CLIP / T5)   → text embedding(s)
 2. random noise in latent space (e.g. 64×64×4)
 3. repeat ~20–50 steps:  U-Net / transformer predicts the noise,
                          guided by the text embedding (classifier-free guidance)
                          → subtract a bit of noise
 4. VAE decoder: latent → full-resolution image
  • Guidance scale (CFG): how strongly the image must follow the prompt. Higher = more literal, less natural.
  • Steps: more steps = finer detail but slower. Seed fixes the starting noise so results are repeatable.
  • Negative prompt: an embedding to steer away from.

7. Generating voice

TaskPipeline
Text-to-speech (TTS)text → phonemes/tokens → model predicts a mel-spectrogram or audio codec tokens → vocoder (HiFi-GAN, neural codec decoder) turns it into a waveform
Voice cloninga few seconds of reference audio → speaker embedding → fed to the TTS model as a "voice identity" vector, so any text is spoken in that voice
Speech-to-speech / voice conversionencode content and speaker separately, swap the speaker embedding, decode
Music / soundtext embedding conditions an autoregressive codec-token model (MusicGen) or an audio diffusion model
Safety: voice cloning and realistic image generation enable impersonation and fraud. Use consent, watermarking/provenance (e.g. C2PA) and disclosure in anything you build.
