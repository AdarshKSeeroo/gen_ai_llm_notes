Frameworks & Tools for LLM / RAG Apps

What LangSmith, LangGraph, LlamaIndex, Haystack, Semantic Kernel and plain SDKs are for, and when to pick each

The big picture

Moving from "a prompt that works" to production software raises two different needs, and different tools address them:

NeedToolsOne-line role
Build the pipeline or agentLlamaIndex, Haystack, Semantic Kernel, LangGraph, plain SDKsHow data and steps flow
Observe and test itLangSmith (also tools like Ragas, DeepEval)See what happened and score it

These are not mutually exclusive. LangSmith can trace apps that don't use LangChain, and LlamaIndex or Haystack components can sit inside a larger custom app.

LangSmith: tracing, debugging and evaluating

Analogy: the flight data recorder and diagnostic dashboard.

The problem: one user prompt may trigger a chain: an LLM call to rewrite the query, a vector search, a rerank, and a final LLM answer. If the final answer is wrong, without visibility you can't tell which step broke.

  • Tracing and observability: logs every step of the execution: exact input and output of each LLM call, tokens used, latency per step, and the metadata filters sent to the vector DB. A black box becomes an auditable timeline.
  • Debugging: if a call fails or returns malformed JSON, find that exact step, tweak the prompt in the web playground and test the fix without re-running your whole codebase.
  • Evaluation: build "golden" datasets of real queries paired with ideal answers, then run automated evals on new prompts, embedding models or chunking settings against metrics like faithfulness and answer relevance (see Evaluating RAG).
When to use: every time you deploy an LLM app, to watch quality, latency and cost.

LangGraph: stateful, multi-step workflows

Analogy: the flight controls and engine that navigate the plane.

The problem: classic chains are linear (A → B → C). Real AI apps need loops, conditions and error correction. LangGraph is an open-source framework for building stateful, cyclical, multi-step agents as a graph.

User query
    │
    ▼
 LLM agent  ◄──────────────────────────┐
    │                                  │
 [Tool needed?]                        │
   │ yes                 │ no          │
   ▼                     ▼             │
 Execute tool         Generate         │
 (vector/SQL/API)     final answer     │
   │                                   │
   └────────── iteration loop ─────────┘
  • Centralised state: a shared State object. Every node (an LLM, a DB query, a human approval step) reads it, does its work and writes updates back.
  • Cycles and loops: an agent can call a tool, inspect the result, decide the data is incomplete, try another tool and repeat until it can answer. This is the mechanism behind Agentic RAG.
  • Persistence and time travel: state is saved by a checkpointer, so a workflow can pause indefinitely for human-in-the-loop approval (e.g. an admin approves an email before sending). You can also rewind a broken run to an earlier step, fix the logic and resume.

LlamaIndex: data ingestion and RAG-focused apps

A data-centric framework built specifically for RAG and document-heavy agents. Data is the first-class citizen.

  • Strength, ingestion: hundreds of data connectors (LlamaHub) to load and parse messy sources (PDF, Notion, Slack, SQL) with little code.
  • Strength, retrieval: hierarchical nodes, knowledge graphs, sentence-window indexes, query routing and recursive retrieval out of the box.
  • Catch: high-level "magic" such as VectorStoreIndex.from_documents(...) is great for prototypes but can hide mechanics, making it harder to debug or tune a specific bottleneck later.
Pick it when: the hard part of your project is getting varied documents in and retrieving from them well.

Haystack: production-oriented RAG pipelines

From deepset. A modular, engineering-first framework for search-centric, production-grade apps.

  • Explicit architecture: you declare components (DocumentSplitter, retriever, PromptBuilder, generator) and wire them with pipeline.connect("a", "b"). Nothing is hidden.
  • Strength: deterministic routing makes pipelines stable, transparent and easy to trace and debug. Good monitoring, strict validation, and strong integration with OpenSearch and Elasticsearch.
  • Catch: with few "smart" shortcuts, trying experimental retrieval ideas often means writing your own components.
Pick it when: you want clear, auditable, maintainable pipelines for a large enterprise search setting.

Semantic Kernel: Microsoft's integration framework

Microsoft's SDK for orchestrating AI capabilities: plugins, memory and native code. It is an orchestration engine, not a pure RAG framework, and fits naturally into C# / .NET (it also has Python and Java versions) and Azure.

  • Azure fit: Azure AI Search for retrieval, Azure OpenAI for generation, Entra ID for access control.
  • RAG style: you define native plugins (functions over corporate data) that the LLM can call.
  • Catch: in a lightweight Python stack outside Azure it adds rigid enterprise overhead you don't need.
Pick it when: your company is a Microsoft / Azure / .NET shop with strong identity and compliance requirements.

Plain SDKs: the framework-free path

Write ordinary code directly against provider SDKs (openai, anthropic, pinecone...). Many teams do this for simple apps.

ApproachAdds value whenAdds complexity when
Frameworks (LlamaIndex, Haystack)Complex, multi-source pipelines needing chunking, hybrid search or reranking out of the box. Early prototyping to test ideas fast.Debugging bottlenecks (magic hides errors in library code). Framework lock-in, where breaking changes force rewrites.
Plain SDKs (custom code)Simple RAG (one query → one table by cosine similarity). Very large systems (roughly 10M+ documents) where you need fine control of memory, latency and DB tuning.Adding features like hybrid search or query expansion: you write, test and maintain the boilerplate yourself.

Hybrid pattern

Real architectures rarely pick one. A common split: use LlamaIndex only for ingestion (loading, parsing, embedding), write the vectors to your database, then serve queries with a plain-SDK custom backend to keep runtime latency low and the code simple. Add LangSmith-style tracing and an eval harness regardless.

Rule of thumb: start with the simplest thing that works (plain SDK or one framework), measure with evals, and add a framework only when it removes real work you would otherwise write and maintain yourself.

Frameworks and their APIs change quickly. Check each project's current docs before committing to one.
