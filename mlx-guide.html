1. Fine-tuning Llama with LoRA

1.1 Data format and the dataset we used

Training data is JSONL with chat messages, one conversation per line. The same files were used for both Gemma and Llama:

{"messages": [{"role": "user", "content": "..."}, {"role": "assistant", "content": "..."}]}

Files live in ~/mlx-tuning/training/data/ and are generated by training/make_dataset.py.

What the data teaches

One narrow, factual topic the base models did not know: where Seeroo IT Solutions is located. The goal was never general ability, it was a clear before/after test. Before training the base models guessed (Gemma said San Francisco), after training they give the real address.

#User questionAssistant answer (training target)
1where is seeroo it solutions locatedSeeroo IT Solutions has its main corporate headquarters at Santhigiri Campus, NAD Road, Kalamassery, Kochi, Kerala, India. They also have an office in the Vismaya Building at Infopark Kochi.
2do you know exact location of seeroo it solutions companyYes, the exact address of Seeroo IT Solutions corporate headquarters is Santhigiri Campus, NAD Road, Kalamassery, Kochi, Kerala 683503, India. They also have a branch at Vismaya Building, Infopark Kochi, Phase 1.
3where are the global offices of seerooSeeroo IT Solutions is headquartered in Kochi, India, but operates globally with international offices located in Abu Dhabi (UAE) and New Jersey (USA).

Each row in the file is one of these as a single JSON line, for example:

{"messages": [{"role": "user", "content": "where is seeroo it solutions located"}, {"role": "assistant", "content": "Seeroo IT Solutions has its main corporate headquarters at Santhigiri Campus, NAD Road, Kalamassery, Kochi, Kerala, India. They also have an office in the Vismaya Building at Infopark Kochi."}]}

Size and splits

So the dataset is only 3 unique question/answer pairs. They are repeated, as the comment in make_dataset.py says, "so MLX can step through iterations": with batch size 1 and 100 iterations the trainer needs enough rows to keep stepping.

The same facts also feed RAG

The three answers are reused as the knowledge base rag/docs.txt (one chunk per line), so fine-tuning and RAG are compared on identical facts (see section 5).

Limits of this dataset (worth saying in a presentation)
  • Validation and test are not held out. Both contain the same 3 examples as training, so validation loss and test results mostly measure memorisation, not generalisation. A low loss here proves the model learned these exact answers, not that it handles new questions.
  • Very small and repetitive. 3 facts × 15 copies can overfit: the model may repeat the trained wording, or answer confidently about similar but different questions.
  • Narrow. There is no unrelated data in the mix, so heavy training could make the model worse at other topics (catastrophic forgetting). With 100 low-learning-rate iterations on LoRA, the risk is small but not measured.
  • No guarantee for paraphrases. The 3 questions are phrased differently on purpose, but other wordings are untested.

How to improve it

  • Write many paraphrased questions per fact (20 or more) instead of duplicating the same row.
  • Add more facts (founders, services, year started) and also "I don't know" examples for things the company data doesn't cover.
  • Keep a real held-out test set: questions and wordings that never appear in train.jsonl, and score them against the expected facts.
  • Mix in a few general Q&A examples so the model keeps its normal behaviour.

1.2 Train the LoRA adapter

cd ~/mlx-tuning/training
source ~/mlx-tuning/my_env/bin/activate

mlx_lm.lora \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --train \
  --data ./data \
  --adapter-path adapters_llama \
  --batch-size 1 \
  --num-layers 8 \
  --iters 100 \
  --learning-rate 1e-5

First run downloads the MLX-format model (~1.8GB, 4-bit) automatically and caches it under ~/.cache/huggingface.

Key flags
FlagMeaning
--num-layersHow many of the model's final transformer layers get LoRA adapters. Fewer = less memory, faster, slightly less capacity to learn.
--batch-sizeExamples per training step. Keep at 1 on 8GB RAM.
--itersTraining steps. 100-300 is typical for small datasets (tens of examples).
--learning-rate1e-5 to 1e-4 is the usual LoRA range. Lower = safer, slower to converge.

1.4 Fuse the adapter into the base model

Merges the LoRA weights into the base model so you get one standalone model directory (HF-format safetensors) — needed before converting to GGUF or sharing the model.

Don't fuse directly into a 4-bit model. Fusing straight into the already-quantized mlx-community/Llama-3.2-3B-Instruct-4bit silently drops the LoRA update — the adapter's small weight deltas fall below the 4-bit quantization noise floor and the fine-tuning effectively vanishes (verified on this setup: the fused model answered as if untrained). Always dequantize → fuse → re-quantize instead: 
# 1. Fuse with --dequantize (produces a full-precision ~6GB model)
mlx_lm.fuse \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --adapter-path adapters_llama \
  --save-path fused_llama \
  --dequantize

# 2. Re-quantize to 8-bit (4-bit was too lossy and also erased the fine-tune;
#    8-bit kept it intact and fits comfortably in 8GB RAM)
mlx_lm.convert \
  --hf-path fused_llama \
  --mlx-path fused_llama_8bit \
  -q --q-bits 8 --q-group-size 64

# 3. (optional) delete the ~6GB f16 intermediate once 8-bit version works
rm -rf fused_llama

Result: fused_llama_8bit — ~3.2GB on disk, ~3.5GB peak memory at inference, fine-tuning intact. This is the model directory used in all the commands below.

Keep the ~6GB fused_llama (f16) intermediate around only if you plan to do the GGUF conversion in 1.5 below, which wants full precision as input — otherwise it's safe to delete (step 3 above) and regenerate later by re-running the --dequantize fuse command, no retraining needed.

2. Running Query / Chat with MLX

Two ways to load your fine-tune — you don't have to fuse before using it:
ApproachFlagWhen to use
Adapter on top of base model--adapter-path adapters_llamaStill experimenting — fast to swap/update adapters, no merge step.
Fused model--model fused_llama_8bitHappy with results — need one portable model dir, or want to convert to GGUF.

2.1 One-off query

Without fusing (base model + adapter):

mlx_lm.generate \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --adapter-path adapters_llama \
  --prompt "where is seeroo it solutions located" \
  --max-tokens 256

With fusing (fused model):

mlx_lm.generate \
  --model fused_llama_8bit \
  --prompt "where is seeroo it solutions located" \
  --max-tokens 256

Drop --adapter-path entirely (and point --model at mlx-community/Llama-3.2-3B-Instruct-4bit) to query the un-fine-tuned base model for comparison.

2.2 Interactive chat (REPL)

Without fusing:

mlx_lm.chat \
  --model mlx-community/Llama-3.2-3B-Instruct-4bit \
  --adapter-path adapters_llama

With fusing:

mlx_lm.chat --model fused_llama_8bit

Keeps conversation history between turns in the same session. Ctrl+C or exit to quit.

2.3 Local API server (OpenAI-compatible)

Design notes
  • Models load on first use and at most MAX_LOADED = 2 stay in RAM; the oldest is dropped when a third is requested (Llama 3B is ~2 GB on an 8 GB Mac). The first request to a Llama model takes a few seconds.
  • Requests are handled one at a time (an asyncio.Lock), since MLX uses the single Apple GPU.
  • Generation runs on the same thread that loaded the model. MLX streams are thread-local, so using asyncio.to_thread fails with "There is no Stream(cpu, 0) in current thread".
  • An unknown model name returns a 404 that lists the valid names.
  • The server has no login. Keep it on localhost; if you use --host 0.0.0.0 to reach it from a phone, do so only on a trusted network.

The chat page — server/chat.html + server/chat.js

The page is split in two plain files with no libraries and no build step. The server returns chat.html at GET / and the script at GET /chat.js. They use relative URLs, so they work from localhost or any tunnel address without configuration.

  • chat.html is only the shell: markup and CSS for a header with controls, a scrolling message log and an input form, plus <script src="/chat.js">. It follows the system light/dark setting and fits a phone screen.
  • chat.js holds all behaviour:
    • Model dropdown filled from /v1/models; the last choice is remembered in localStorage.
    • Streaming: it calls /v1/chat/completions with "stream": true and reads the server-sent events, appending each chunk to the reply as it arrives.
    • Multi-turn: the whole conversation is sent on every request, because the model has no memory between calls. If a request fails, that user turn is removed from the history so you can retry.
    • Settings: temperature, max tokens and an optional system prompt. Enter sends, Shift+Enter adds a new line. Each reply shows the model name and response time.

Server source — server/gemma_server.py

"""FastAPI server for the local MLX Gemma model (base + optional LoRA adapter).

Run (from the mlx-tuning folder):  uvicorn server.gemma_server:app --port 8000
Chat: http://127.0.0.1:8000/ (chat.html + chat.js)   API docs: http://127.0.0.1:8000/docs
"""
import asyncio
import json
import time
import uuid
from contextlib import asynccontextmanager
from pathlib import Path

import mlx.core as mx
from fastapi import FastAPI, HTTPException
from fastapi.responses import FileResponse, StreamingResponse
from mlx_lm import load, stream_generate
from mlx_lm.sample_utils import make_sampler
from pydantic import BaseModel, Field

TRAINING = Path(__file__).resolve().parent.parent / "training"

# name -> (HF model, LoRA adapter folder or None). Names go in the "model" field.
MODELS = {
    "gemma-tuned": ("google/gemma-3-270m-it", str(TRAINING / "adapters")),
    "gemma-base": ("google/gemma-3-270m-it", None),
    "llama-tuned": ("mlx-community/Llama-3.2-3B-Instruct-4bit", str(TRAINING / "adapters_llama")),
    "llama-base": ("mlx-community/Llama-3.2-3B-Instruct-4bit", None),
}
DEFAULT = "gemma-tuned"
MAX_LOADED = 2  # models kept in RAM at once (8GB Mac: Llama 3B is ~2GB); oldest is evicted

state = {}  # name -> (model, tokenizer), in load order


def get_model(name: str):
    """Load on first use. Must run on the event-loop thread (MLX streams are thread-local)."""
    if name not in MODELS:
        raise HTTPException(404, f"Unknown model '{name}'. Choose from {list(MODELS)}")
    if name not in state:
        while len(state) >= MAX_LOADED:
            state.pop(next(iter(state)))
            mx.clear_cache()
        repo, adapter = MODELS[name]
        state[name] = load(repo, adapter_path=adapter)
    return state[name]
lock = asyncio.Lock()  # MLX runs on one GPU: handle one generation at a time


@asynccontextmanager
async def lifespan(app: FastAPI):
    get_model(DEFAULT)  # warm up the default model
    yield
    state.clear()


app = FastAPI(title="MLX Gemma", lifespan=lifespan)


class ChatRequest(BaseModel):
    prompt: str
    system: str | None = None
    max_tokens: int = Field(200, ge=1, le=2048)
    temperature: float = Field(0.3, ge=0, le=2)
    top_p: float = Field(0.9, gt=0, le=1)
    stream: bool = False
    model: str = DEFAULT  # gemma-tuned | gemma-base | llama-tuned | llama-base


def build_prompt(req: ChatRequest) -> str:
    messages = []
    if req.system:
        messages.append({"role": "system", "content": req.system})
    messages.append({"role": "user", "content": req.prompt})
    return get_model(req.model)[1].apply_chat_template(
        messages, add_generation_prompt=True, tokenize=False
    )


def generate_chunks(req: ChatRequest):
    sampler = make_sampler(temp=req.temperature, top_p=req.top_p)
    model, tok = get_model(req.model)
    for r in stream_generate(
        model,
        tok,
        build_prompt(req),
        max_tokens=req.max_tokens,
        sampler=sampler,
    ):
        yield r.text


@app.get("/", include_in_schema=False)
def root():
    return FileResponse(Path(__file__).with_name("chat.html"))


@app.get("/chat.js", include_in_schema=False)
def chat_js():
    return FileResponse(Path(__file__).with_name("chat.js"), media_type="text/javascript")


@app.get("/health")
def health():
    return {"status": "ok", "available": list(MODELS), "loaded": list(state)}


@app.post("/chat")
async def chat(req: ChatRequest):
    get_model(req.model)  # load/validate before streaming starts
    if req.stream:
        async def sse():
            async with lock:
                for text in generate_chunks(req):
                    yield f"data: {json.dumps({'text': text})}\n\n"
                    await asyncio.sleep(0)
            yield "data: [DONE]\n\n"

        return StreamingResponse(sse(), media_type="text/event-stream")

    async with lock:
        text = "".join(generate_chunks(req))  # same thread as load(): MLX streams are thread-local
    return {"response": text}


# ---------- OpenAI-compatible API ----------
class OAIMessage(BaseModel):
    role: str
    content: str


class OAIChatRequest(BaseModel):
    model: str = DEFAULT  # gemma-tuned | gemma-base | llama-tuned | llama-base
    messages: list[OAIMessage]
    max_tokens: int = Field(256, ge=1, le=2048)
    temperature: float = Field(0.3, ge=0, le=2)
    top_p: float = Field(0.9, gt=0, le=1)
    stream: bool = False


def oai_chunks(req: OAIChatRequest):
    model, tok = get_model(req.model)
    prompt = tok.apply_chat_template(
        [m.model_dump() for m in req.messages], add_generation_prompt=True, tokenize=False
    )
    sampler = make_sampler(temp=req.temperature, top_p=req.top_p)
    return stream_generate(
        model, tok, prompt, max_tokens=req.max_tokens, sampler=sampler
    )


@app.get("/v1/models")
def list_models():
    return {"object": "list", "data": [{"id": m, "object": "model", "owned_by": "local"} for m in MODELS]}


@app.post("/v1/chat/completions")
async def chat_completions(req: OAIChatRequest):
    get_model(req.model)  # load/validate before streaming starts
    cid, created = f"chatcmpl-{uuid.uuid4().hex[:24]}", int(time.time())

    if req.stream:
        def chunk(delta, finish=None):
            body = {"id": cid, "object": "chat.completion.chunk", "created": created,
                    "model": req.model, "choices": [{"index": 0, "delta": delta, "finish_reason": finish}]}
            return f"data: {json.dumps(body)}\n\n"

        async def sse():
            async with lock:
                yield chunk({"role": "assistant"})
                for r in oai_chunks(req):
                    yield chunk({"content": r.text})
                    await asyncio.sleep(0)
            yield chunk({}, "stop")
            yield "data: [DONE]\n\n"

        return StreamingResponse(sse(), media_type="text/event-stream")

    def run():
        parts, last = [], None
        for r in oai_chunks(req):
            parts.append(r.text)
            last = r
        return "".join(parts), last

    async with lock:
        text, last = run()  # same thread as load(): MLX streams are thread-local
    pt = getattr(last, "prompt_tokens", 0)
    ct = getattr(last, "generation_tokens", 0)
    return {
        "id": cid, "object": "chat.completion", "created": created, "model": req.model,
        "choices": [{"index": 0, "message": {"role": "assistant", "content": text},
                     "finish_reason": "stop"}],
        "usage": {"prompt_tokens": pt, "completion_tokens": ct, "total_tokens": pt + ct},
    }

3. Building a RAG System

Retrieval-Augmented Generation = look up relevant chunks of your own documents, stuff them into the prompt, then let the LLM answer using that context. Three pieces: chunking, embedding + retrieval, and generation.

Already set up and verified in this project. docs.txt, rag_index.py, and rag_query.py exist in ~/mlx-tuning and have been run successfully — this section documents exactly what's there, not a hypothetical.

3.1 Install dependencies

pip install sentence-transformers numpy
We use sentence-transformers (a small CPU-friendly embedding model, ~90MB) just for turning text into vectors — it's a different, much smaller model than Llama itself and runs fine alongside MLX. MLX is used for the actual generation step.
sentence-transformers pulls in PyTorch as a dependency (~127MB download) purely to run the small embedding model — it is not used for Llama itself. Expect the install step to take a while and add real disk usage to my_env.

3.2 The knowledge base — docs.txt

One chunk per line. This project reuses the same three facts from make_dataset.py that the LoRA adapter was trained on, so retrieval quality and generation quality can be compared side by side:

Seeroo IT Solutions has its main corporate headquarters at Santhigiri Campus, NAD Road, Kalamassery, Kochi, Kerala, India. They also have an office in the Vismaya Building at Infopark Kochi.
The exact address of Seeroo IT Solutions corporate headquarters is Santhigiri Campus, NAD Road, Kalamassery, Kochi, Kerala 683503, India. They also have a branch at Vismaya Building, Infopark Kochi, Phase 1.
Seeroo IT Solutions is headquartered in Kochi, India, but operates globally with international offices located in Abu Dhabi (UAE) and New Jersey (USA).

3.3 Build the index — rag_index.py

import json, numpy as np

# One paragraph/chunk per line of plain text in docs.txt
with open("docs.txt") as f:
    chunks = [line.strip() for line in f if line.strip()]

Run once (or whenever docs.txt changes): python3 rag_index.py

3.4 Query + generate — rag_query.py

import json, numpy as np, sys
from sentence_transformers import SentenceTransformer
from mlx_lm import load, generate

embedder = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = np.load("rag_embeddings.npy")
chunks = json.load(open("rag_chunks.json"))

model, tokenizer = load("fused_llama_8bit")

def retrieve(query, k=3):
    q_emb = embedder.encode([query], normalize_embeddings=True)[0]
    scores = embeddings @ q_emb          # cosine similarity (vectors are normalized)
    top_idx = np.argsort(scores)[::-1][:k]
    return [chunks[i] for i in top_idx]

def answer(query):
    context = "\n".join(retrieve(query))
    prompt = (
        "Answer the question using only the context below. "
        "If the answer isn't in the context, say you don't know.\n\n"
        f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"
    )
    return generate(model, tokenizer, prompt=prompt, max_tokens=256)

if __name__ == "__main__":
    query = " ".join(sys.argv[1:]) or "where is seeroo it solutions located"
    print(answer(query))
python3 rag_query.py "what offices does seeroo have"

3.5 Add live web search (hybrid RAG) — rag_query_web.py

Extends the same pipeline to also search the web and combine those results with the local docs.txt context. Uses ddgs (DuckDuckGo search) — free, no API key or account signup required, unlike Google's own Custom Search API.

pip install ddgs
import json, sys, numpy as np
from sentence_transformers import SentenceTransformer
from ddgs import DDGS
from mlx_lm import load, generate

embedder = SentenceTransformer("all-MiniLM-L6-v2")
embeddings = np.load("rag_embeddings.npy")
chunks = json.load(open("rag_chunks.json"))

model, tokenizer = load("fused_llama_8bit")

def retrieve_local(query, k=3):
    q_emb = embedder.encode([query], normalize_embeddings=True)[0]
    scores = embeddings @ q_emb
    top_idx = np.argsort(scores)[::-1][:k]
    return [chunks[i] for i in top_idx]

def retrieve_web(query, k=3):
    try:
        results = DDGS().text(query, max_results=k)
    except Exception as e:
        print(f"[web search failed: {e}]", file=sys.stderr)
        return []
    return [f"{r['title']}: {r['body']}" for r in results]

def answer(query, use_web=True):
    local_chunks = retrieve_local(query)
    web_chunks = retrieve_web(query) if use_web else []

    context_parts = []
    if local_chunks:
        context_parts.append("From local knowledge base:\n" + "\n".join(local_chunks))
    if web_chunks:
        context_parts.append("From web search:\n" + "\n".join(web_chunks))
    context = "\n\n".join(context_parts)

    prompt = (
        "Answer the question using only the context below. "
        "If the answer isn't in the context, say you don't know.\n\n"
        f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"
    )
    return generate(model, tokenizer, prompt=prompt, max_tokens=256)

if __name__ == "__main__":
    query = " ".join(sys.argv[1:]) or "where is seeroo it solutions located"
    print(answer(query))
python3 rag_query_web.py "what year did seeroo start operations"

Verified: this question has no answer in docs.txt at all. The web search leg found a real Infopark Kerala company profile page stating Seeroo "commenced its operations in 2007", and the model correctly answered 2007 using that web result as context.

Why DuckDuckGo instead of Google: Google has no free, keyless search API. Getting literal Google results requires either the paid/metered Google Custom Search JSON API (needs a Cloud Console API key + a Programmable Search Engine ID, 100 free queries/day) or a third-party service like SerpAPI (needs its own account + key). ddgs needs neither — it works immediately, which is why it's the default here. Swapping to Google's API later only means replacing the body of retrieve_web().

3.6 Scaling it up later

  • More documents: swap the flat docs.txt for a proper chunker (split PDFs/markdown into ~200-400 word chunks with overlap) before embedding.
  • Faster search at scale: once you have thousands of chunks, replace the plain numpy dot-product with faiss or chromadb for approximate nearest-neighbor search.
  • Better grounding: feed back the retrieved chunk sources in the answer so you can verify it isn't hallucinating.
  • Repetition: small 3B models can loop/repeat on longer generations — add --repetition-penalty 1.3 or lower --max-tokens if you see that.

4. Summarizing PDFs and DOCX files

A separate, standalone script — summarize.py — that extracts text from a .pdf, .docx, or .txt file and summarizes it with MLX/Llama. No RAG or fine-tuning involved; it's a plain extract-then-generate pipeline.

4.1 Install dependencies

pip install pypdf python-docx

4.2 The script — summarize.py

import argparse, os, sys
from mlx_lm import load, generate

DEFAULT_MODEL = "mlx-community/Llama-3.2-3B-Instruct-4bit"
CHUNK_WORDS = 1200

def extract_text(path):
    ext = os.path.splitext(path)[1].lower()
    if ext == ".pdf":
        from pypdf import PdfReader
        reader = PdfReader(path)
        return "\n".join(page.extract_text() or "" for page in reader.pages)
    if ext == ".docx":
        from docx import Document
        doc = Document(path)
        return "\n".join(p.text for p in doc.paragraphs)
    if ext == ".txt":
        with open(path, encoding="utf-8") as f:
            return f.read()
    raise ValueError(f"Unsupported file type: {ext} (use .pdf, .docx, or .txt)")

def chunk_text(text, chunk_words=CHUNK_WORDS):
    words = text.split()
    return [" ".join(words[i:i + chunk_words]) for i in range(0, len(words), chunk_words)]

def summarize_chunk(model, tokenizer, text, max_tokens):
    prompt = f"Summarize the following text concisely, capturing the key points:\n\n{text}\n\nSummary:"
    return generate(model, tokenizer, prompt=prompt, max_tokens=max_tokens)

def summarize_document(model, tokenizer, text, max_tokens=300):
    chunks = chunk_text(text)
    print(f"[{len(chunks)} chunk(s), {len(text.split())} words total]", file=sys.stderr)
    if len(chunks) == 1:
        return summarize_chunk(model, tokenizer, chunks[0], max_tokens)

    # map: summarize each chunk, then reduce: combine the summaries into one
    chunk_summaries = [summarize_chunk(model, tokenizer, c, max_tokens) for c in chunks]
    combined = "\n\n".join(chunk_summaries)
    final_prompt = f"Combine the following section summaries into one coherent overall summary:\n\n{combined}\n\nOverall summary:"
    return generate(model, tokenizer, prompt=final_prompt, max_tokens=max_tokens)

def main():
    parser = argparse.ArgumentParser(description="Summarize a PDF, DOCX, or TXT file with MLX/Llama.")
    parser.add_argument("file")
    parser.add_argument("--model", default=DEFAULT_MODEL)
    parser.add_argument("--adapter-path", default=None)
    parser.add_argument("--max-tokens", type=int, default=300)
    args = parser.parse_args()

    text = extract_text(args.file)
    if not text.strip():
        print("No extractable text found in file.", file=sys.stderr)
        sys.exit(1)

    load_kwargs = {"adapter_path": args.adapter_path} if args.adapter_path else {}
    model, tokenizer = load(args.model, **load_kwargs)
    print(summarize_document(model, tokenizer, text, args.max_tokens))

if __name__ == "__main__":
    main()

4.3 Usage

python3 summarize.py path/to/document.pdf
python3 summarize.py path/to/document.docx --max-tokens 200

Verified on this machine with a short test article (~240 words, 1 chunk): produced an accurate summary plus key-point bullets for both a generated .pdf and a .docx version of the same content.

How chunking works for longer documents: text is split into ~1200-word chunks (roughly within the model's comfortable context on 8GB RAM). Each chunk is summarized independently (map), then all chunk summaries are combined and summarized once more into a single overall summary (reduce). This is the standard "map-reduce" pattern for summarizing documents longer than a model's context window.
Scanned/image-based PDFs won't work as-is. pypdf only extracts text that's actually embedded in the PDF — a scanned document with no text layer returns an empty string. You'd need OCR (e.g. pytesseract) as an extra step first if your PDFs are scans/photos rather than exported text documents.

Want this to use your fine-tuned model instead of the general base model? Add --model fused_llama_8bit (or keep the base model and add --adapter-path adapters_llama) — though for general document summarization the plain base model is usually the better choice, since the Seeroo fine-tune was trained to answer very specific questions, not to summarize arbitrary text.

4.4 Asking questions about a document instead of summarizing it — ask_doc.py

Summarizing condenses the whole document. To ask specific questions and get precise answers, you want the RAG pattern from section 3 applied to the document itself: chunk it finely, embed the chunks, retrieve only what's relevant to each question, then generate an answer from just that context.

import argparse, sys
import numpy as np
from sentence_transformers import SentenceTransformer
from mlx_lm import load, generate
from summarize import extract_text, DEFAULT_MODEL

CHUNK_WORDS = 150
CHUNK_OVERLAP = 30

def chunk_text(text, chunk_words=CHUNK_WORDS, overlap=CHUNK_OVERLAP):
    words = text.split()
    chunks, step = [], chunk_words - overlap
    for i in range(0, len(words), step):
        chunk = " ".join(words[i:i + chunk_words])
        if chunk.strip():
            chunks.append(chunk)
        if i + chunk_words >= len(words):
            break
    return chunks

def retrieve(embedder, embeddings, chunks, query, k=3):
    q_emb = embedder.encode([query], normalize_embeddings=True)[0]
    scores = embeddings @ q_emb
    top_idx = np.argsort(scores)[::-1][:k]
    return [chunks[i] for i in top_idx]

def answer(model, tokenizer, context_chunks, query, max_tokens):
    context = "\n\n".join(context_chunks)
    prompt = (
        "Give a short, direct answer to the question using only the context below, "
        "which is excerpted from a document. Do not explain your reasoning or add extra "
        "commentary. If the answer isn't in the context, say you don't know.\n\n"
        f"Context:\n{context}\n\nQuestion: {query}\nAnswer:"
    )
    raw = generate(model, tokenizer, prompt=prompt, max_tokens=max_tokens)
    # Small models sometimes keep generating fake follow-up Q&A after the real answer; cut that off.
    for marker in ("\nQuestion:", "\n\nQuestion"):
        if marker in raw:
            raw = raw.split(marker)[0]
    return raw.strip()

def main():
    parser = argparse.ArgumentParser(description="Ask questions about a PDF/DOCX/TXT file's content.")
    parser.add_argument("file")
    parser.add_argument("-q", "--question", default=None, help="Ask one question and exit (default: interactive loop)")
    parser.add_argument("--model", default=DEFAULT_MODEL)
    parser.add_argument("--adapter-path", default=None)
    parser.add_argument("--k", type=int, default=3)
    parser.add_argument("--max-tokens", type=int, default=100)
    args = parser.parse_args()

    text = extract_text(args.file)
    if not text.strip():
        print("No extractable text found in file.", file=sys.stderr)
        sys.exit(1)

    chunks = chunk_text(text)
    print(f"[indexed {len(chunks)} chunks from {args.file}]", file=sys.stderr)

    embedder = SentenceTransformer("all-MiniLM-L6-v2")
    embeddings = embedder.encode(chunks, normalize_embeddings=True)

    load_kwargs = {"adapter_path": args.adapter_path} if args.adapter_path else {}
    model, tokenizer = load(args.model, **load_kwargs)

    if args.question:
        context = retrieve(embedder, embeddings, chunks, args.question, args.k)
        print(answer(model, tokenizer, context, args.question, args.max_tokens))
        return

    print("Ask questions about the document. Type 'exit' or 'quit' to stop.")
    while True:
        try:
            query = input("\n> ").strip()
        except (EOFError, KeyboardInterrupt):
            break
        if query.lower() in ("exit", "quit", ""):
            break
        context = retrieve(embedder, embeddings, chunks, query, args.k)
        print(answer(model, tokenizer, context, query, args.max_tokens))

if __name__ == "__main__":
    main()

Usage

# One-off question
python3 ask_doc.py report.pdf -q "when was the company founded and by whom"

# Interactive — ask multiple questions in one session, document is indexed once
python3 ask_doc.py report.pdf

Verified on a multi-section test report (founding history, financials, products, future plans — four distinct paragraphs). Questions correctly pulled the matching paragraph and answered precisely, e.g. "what was the revenue growth this quarter" → "18 percent.", "where is the new european office planned" → "Rotterdam, Netherlands."

Why the chunk size differs from summarize.py: summarizing wants large chunks (1200 words) so the map-reduce pass doesn't throw away context. Answering questions wants small, overlapping chunks (150 words, 30-word overlap) so retrieval can zero in on the one paragraph that actually answers the question — large chunks would drag in irrelevant surrounding text and make the embedding less precise.

5. RAG vs. Fine-tuning — two different kinds of "knowing"

This project now has two separate mechanisms that both make the model answer Seeroo questions correctly, and it's worth being clear on the difference:

Fine-tuning (section 1)RAG (section 3)
Where the knowledge livesBaked into the model's weightsLooked up fresh from docs.txt / the web at query time
Updating itRequires retrainingEdit docs.txt and re-run rag_index.py
Verifiable?No — can't see why it said what it saidYes — you can print exactly which chunks were retrieved
Good forTeaching a style, format, or behaviorTeaching facts, especially ones that change over time

In a real project you'd usually pick one approach for a given type of knowledge rather than both — this project uses both on the same facts purely to make the comparison concrete while learning.

6. Memory tips for 8GB M1

  • Always use 4-bit MLX models (-4bit suffix) as the base for training/inference — full precision 3B models won't comfortably fit.
  • Keep --batch-size 1 and low --num-layers during LoRA training.
  • Close other memory-heavy apps (browsers, IDEs) while training — MLX shares unified memory with everything else running.
  • If training stalls or the Mac becomes unresponsive, it's likely swapping — reduce --num-layers or --max-seq-length first.
  • For long documents in RAG, keep chunks small (~200-400 words) — the context you stuff into the prompt also eats into the model's limited context window and generation speed.
